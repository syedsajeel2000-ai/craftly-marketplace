# Craftly — Etsy-Inspired Marketplace

A fully functional, two-sided e-commerce marketplace for handmade, vintage and digital goods.
Every feature is real: accounts, carts, orders, inventory, reviews and wishlists are persisted in a
**Turso (libSQL)** database and read/written through a server-side API. No fake buttons, no
localStorage-as-a-database, no hardcoded product arrays.

> Original implementation — not affiliated with Etsy. All artwork, code and copy are our own.

---

## Tech stack

| Layer    | Technology |
| -------- | ---------- |
| Frontend | React 18, React Router 6, Tailwind CSS v4 (design tokens in `src/index.css`), Vite 6 |
| Backend  | Express 4, session cookies (httpOnly), bcrypt password hashing |
| Database | **Turso / libSQL** via `@libsql/client` — local `file:` DB by default, Turso cloud in production |
| Art      | Original SVG product/category/avatar artwork generated by `scripts/generate-images.mjs` |

## Quick start

```bash
# 1. Install dependencies
npm install

# 2. Configure environment (optional for local dev)
cp .env.example .env
#   → Leave TURSO_DATABASE_URL empty (or set file:./data/craftly.db) to use the local DB.
#   → For Turso cloud: TURSO_DATABASE_URL=libsql://<db-name>-<org>.turso.io
#                      TURSO_AUTH_TOKEN=<your-token>       (from `turso db show` / `turso db tokens create`)

# 3. Create + seed the database (idempotent, safe to re-run)
npm run db:init

# 4. Run API (8787) + client (5273) together
npm run dev
```

Open **http://localhost:5273**.

| Script | Purpose |
| ------ | ------- |
| `npm run dev` | API + Vite client concurrently |
| `npm run dev:server` / `dev:client` | Run each side separately |
| `npm run db:migrate` | Apply `db/schema.sql` |
| `npm run db:seed` | Seed 15 categories, demo users, 63 products, 222 reviews |
| `npm run db:bulk` | Bulk catalog: 2,000 more listings + 200 sellers / 140 buyers |
| `npm run db:daily` | Run whichever category generators are due (`-- --all` forces all 15) |
| `npm run db:photos` | Download ~225 real CC-licensed photos to `public/images/photos/` |
| `npm run db:assign-photos` | Point every listing's gallery at those real photos |
| `npm run db:images` | Regenerate unique SVG artwork (fallback when photos aren't downloaded) |
| `npm run db:init` | Migrate + seed + bulk catalog |
| `npm run build` / `npm run preview` | Production client build / preview |
| `npm start` | Production: serves API **and** the built client from one process |
| `npm run test:api` | 97-check end-to-end API test suite (server must be running) |

## Features

### Buyers
- Browse homepage sections loaded live from the DB: hero stats, featured, trending, categories, handmade, vintage, digital, top-rated
- Search (title, description, category, seller name) with URL-driven filters: category, product type, price ranges + custom min/max, rating, availability
- Sorting: recommended, newest, price ↑/↓, highest rated; pagination
- Product detail: image gallery, stock badges, quantity picker, related items, share
- Server-backed cart (quantity update, remove, clear, issue banner) — follows the account across devices
- 3-step checkout (customer → shipping → demo payment) with **server-side total recomputation**
- Order confirmation, order history, order detail
- Purchase-gated reviews (only buyers of a product can review; one review per buyer, aggregates re-computed)
- Wishlist (toggle from any card or product page)
- Account: edit profile, change password
- **Seller storefronts**: every seller's name is a link to `/shop/:username` — cover, bio, member-since, listing/in-review/in-stock counts, category chips, sortable + paginated grid
- **Shop directory** at `/shops` — all 200 sellers, searchable by name, ranked by catalogue size, each linking to its storefront

### Product photography
Listings show **real photographs**, not generated artwork. `npm run db:photos` pulls a
curated pool from [Openverse](https://openverse.org) (which indexes Creative Commons media)
into `public/images/photos/`, and `npm run db:assign-photos` rewrites `products.images` so
each listing gets three photos drawn from the pool for **its own category**.

- **Licences**: only CC0, Public Domain Mark and CC BY are accepted. NC and ND are
  rejected — this looks like a real storefront, and non-commercial / no-derivatives photos
  are not safe to ship there. Every accepted photo is attributed in
  [`public/images/photos/CREDITS.md`](public/images/photos/CREDITS.md) and recorded
  machine-readably in `manifest.json`.
- **Quality filtering**: the pool rejects clip-art, watermarks, museum/archaeological shots,
  food photography, cosplay galleries and off-topic subjects, and de-duplicates Openverse
  galleries that shoot the same object six times. Photo file names are derived from a hash of
  the source URL, so re-running the fetch re-uses files already on disk and can never
  attribute an image to the wrong creator.
- **Curated pool, not unique per listing**: 15 photos per category (225 total) rotate across
  the ~2,400 listings, offset by a hash of the product id so neighbouring listings don't open
  on the same photo.
- Every path that creates a listing draws from the same pool via `scripts/photo-pool.js`:
  `db:seed`, `db:bulk`, the daily batch and `db:assign-photos`. So a **fresh `npm run db:init`
  produces real photos too** (as long as `db:photos` has been run first); each falls back to
  the generated SVG artwork when the photos aren't on disk, which is also what
  `npm run db:images` regenerates.
- Re-running `db:assign-photos` is a no-op once every listing is converted.

### Sellers
- One-click **Become a seller** (`/seller?setup=1`) — upgrades the account role
- Dashboard: overview stats (revenue, orders, products, units), 6-month revenue chart, low-stock alerts
- Product CRUD: create/edit listings (title, description, price, category, type, images, stock, flags)
- Publish/unpublish toggle; delete removes the row, or deactivates it (with order history preserved) when orders exist
- Inventory manager: add / subtract / set stock with a full activity log (every checkout writes a log entry too)
- Orders containing their items, with per-order revenue
- Shop profile editor
- The same profile is publicly browsable at `/shop/:username` — anyone can open a seller's storefront without signing in

### Platform
- Real Turso persistence: users, sessions, products, categories, carts, cart_items, orders, order_items, reviews, wishlist, inventory_logs
- Relational schema with foreign keys, indexes, timestamps and constraints (`db/schema.sql`)
- Checkout is **atomic** — order + items + inventory decrement + inventory logs + cart clear happen in one libSQL write transaction
- Data isolation: every query is scoped to the authenticated user; auth guards on cart/checkout/orders/wishlist/profile/seller routes
- Security: bcrypt password hashes, httpOnly session cookies, no credentials in client code, `.env` git-ignored, raw DB errors never leak to clients
- **Every listing has its own artwork** — no shared placeholders: `scripts/generate-images.mjs` derives a deterministic-but-unique SVG per product (palette, composition, glyph and motif seeded from the listing itself) and writes a 3-image gallery per listing
- **15 daily listing generators, one per category** — `scripts/daily-listings.js` runs 15 generators (one for each of the 15 categories); each publishes **25 listings per day** (375/day total), staggered 96 minutes apart so the catalog fills gradually. Every listing gets its own artwork and reviews. Each `(day, category)` batch is claimed once in `daily_batches`, so restarts, races and repeated runs never duplicate — a full re-check is a 0.01s no-op
- **2,000 pre-made listings** — `scripts/seed-bulk.js` fills out the marketplace: 2,000 listings across all 15 categories (6,000 unique images), 4,350 reviews, plus 20 extra sellers and 140 extra buyers, all sharing the demo password
- UI: loading skeletons, empty states, error states with retry, toast notifications (aria-live)
- **Every button has a hover affordance** — a global rule lifts and brightens `button`, `[role=button]`, `summary` and `.btn` on hover. It animates the individual `translate` property (not `transform`) so it composes with Tailwind `active:scale-*` and framer-motion transforms instead of overriding them; tiles that already define their own hover motion are left alone, and reduced-motion users get colour changes only
- **Motion with framer-motion** — animated hero (staggered entrance, scroll parallax, floating listing tiles), scroll-triggered `Reveal`/`Stagger` section reveals, spring hover/tap on product cards, animated route transitions; all of it wrapped in `MotionConfig reducedMotion="user"` so the OS "reduce motion" setting turns everything off
- Responsive from 320px → desktop (mobile drawer nav, filter drawer, sticky mobile buy bar), accessible labels/focus rings/roles
- Custom 404, professional footer, lazy-loaded routes

                             # Info, NotFound

### Database tables
`users`, `user_sessions`, `categories`, `products`, `carts`, `cart_items`, `orders`,
`order_items`, `product_reviews`, `wishlist`, `inventory_logs` — with foreign keys
(e.g. a product belongs to a seller, an order belongs to a buyer and contains many items,
a cart contains many items, a product has many reviews).

### Environment variables (`.env.example`)

```bash
TURSO_DATABASE_URL=        # libsql://… for Turso cloud, or file:./data/craftly.db locally
TURSO_AUTH_TOKEN=          # Turso API token (server-side only — never sent to the browser)
PORT=8787
SESSION_SECRET=            # random hex string for session cookies
```

With no `.env`, the app falls back to the local `file:./data/craftly.db` database, so the project
runs out of the box. `.env` is listed in `.gitignore` and credentials are only read by the server.

## Deploying to Vercel

The app runs as **one deployment serving both the JSON API and the React client**:

| Piece | How it's served |
| ----- | --------------- |
| `/api/*` | `api/index.js` → serverless function wrapping the Express app |
| `/images/*` | Vercel CDN, straight from `public/` (cached 1 year, immutable) |
| `/assets/*` | Vercel CDN, from the Vite `dist/` build (cached 1 year) |
| everything else | rewritten to `index.html` for client-side routing |

### Before you deploy: you need a hosted database

**The local `file:./data/craftly.db` cannot be used in production.** Serverless
filesystems are read-only and reset on every cold start, so the catalogue would be
empty on the next request. Point the app at Turso instead:

```bash
npm i -g turso
turso db create craftly          # free tier
turso db tokens create           # copy the token it prints
turso db show craftly            # copy libsql:// URL + token
```

> **Turso token types matter.** An *organisation* token authenticates against
> Turso's API but is rejected by the database server with
> `invalid JWT token: can't be decoded with any of the existing keys`. You need a
> **database-scoped** token — create it from inside the database (dashboard →
> your DB → Tokens), or with
> `POST /v1/organizations/<org>/databases/<db>/auth/tokens`.

### Deploy

```bash
npx vercel                       # first run: log in, confirm the project link
npx vercel env add TURSO_DATABASE_URL production
npx vercel env add TURSO_AUTH_TOKEN production
npx vercel env add SESSION_SECRET production   # openssl rand -hex 32
npx vercel env add CRON_SECRET production       # any long random string
npx vercel --prod
```

To fill a fresh Turso database with the demo catalogue:

```bash
npm run db:photos                              # once, so listings get real photos
TURSO_DATABASE_URL=libsql://… TURSO_AUTH_TOKEN=… npm run db:init
```

Or copy the catalogue you already have (2,438 listings, 200 sellers, 5,317
reviews) straight into Turso, which keeps it byte-identical to what's on disk:

```bash
TURSO_DATABASE_URL=libsql://… TURSO_AUTH_TOKEN=… npm run db:push
DRY=1 TURSO_DATABASE_URL=… TURSO_AUTH_TOKEN=… npm run db:push   # preview only
```

Check what a deployment would upload before you run it:

```bash
npm run db:deploy-size     # applies .vercelignore, reports files + MB
```

### Serverless notes

- `server/index.js` detects `process.env.VERCEL` and skips `app.listen()`, the
  static middleware and the 60-second listing-generator interval — none of which
  survive on serverless. It exports the app instead, which `api/index.js`
  re-exports as the function handler. The same file still runs locally unchanged.
- New listings are published by **Vercel Cron** hitting `/api/cron/daily` every
  hour (`crons` in `vercel.json`), guarded by `CRON_SECRET`. The daily batches are
  claimed once per `(day, category)` in the database, so overlapping or repeated
  invocations are safe.
- `public/images/photos/manifest.json` is bundled into the function via
  `functions.includeFiles` so the server can pick photos for new listings. The
  bundler emits it under `dist/` rather than `public/`, so
  `scripts/photo-pool.js` probes several known locations instead of assuming one —
  without that, the daily generator would silently fall back to placeholder art
  in production.
- `.vercelignore` keeps `data/`, `dist/` and the ~36 MB of legacy generated SVG
  artwork out of the upload. Nothing references that artwork any more; regenerate
  it locally with `npm run db:images` if you ever need it.
